## Agent最容易在问题不清楚时显得高效

Agent很擅长把一句话迅速变成界面、接口和代码。问题是，如果这句话本身混入了未经确认的假设，Agent也会很快把错误方向做得像模像样。

例如，新增“收藏会话”需要说清员工怎样找回重要内容、收藏关系属于谁、能保留多久。这些答案会改变产品规则，值得持续跟踪。已有收藏按钮的文案或位置调整则可以由Agent在授权范围内直接修改并验证，不需要重新证明整个功能的价值。

先弄清发生了什么，再判断是直接修正局部问题，还是需要改变长期规则。需要REQ的变化再进入本章的需求讨论；每个用户可见变化都填一套材料，会挤掉真正值得讨论的问题。

## 第一步：先描述发生了什么

问题描述要从使用现场开始，而不是从已经想到的功能名称开始。对于本章的例子，可以先写成：

> 员工的会话越来越多。需要再次查看一段重要内容时，员工经常要在列表中反复滚动和打开多个会话，仍然很难快速找到目标。

这段话还不是需求，但它已经说清了谁遇到问题、当时想完成什么任务以及现在受到什么阻碍。接下来可以继续补充：这种情况出现得多不多，哪些员工受到影响，搜索和最近使用是否已经解决了一部分问题，以及我们掌握的是实际观察还是猜测。

Director不需要独自完成调查。Agent可以查看当前产品和代码，整理已有反馈，复现现象，找出相似功能，也可以追问描述中的空白。但Agent此时产出的是调查材料，不是替Director作出的产品决定。

一个有用的问题描述通常能让读者看出：

- 谁在什么情况下遇到了困难；
- 当前实际发生了什么；
- 问题造成了什么影响；
- 哪些内容已经确认，哪些仍然只是推测；
- 为什么这件事值得继续处理。

一次性观察可以留在当前讨论或已有任务记录中。仅换会话、换Agent继续同一项边界清楚的低风险工作，保存简短交接即可；需要独立调查、排期、交给其它工作单元处理，或长期追踪未解决影响时，再为它分配ISSUE编号并登记。完整判断规则见[STD-004](../../00-规范/STD-004-需求流转规范.md)。

## 第二步：判断是否需要ISSUE或REQ(Requirement)

ISSUE和REQ保存的不是同一种东西。ISSUE保存一个需要单独追踪的问题，REQ保存一项需要持续跟踪产品取舍和验收的变化。已授权的单页文案、布局、尺寸、滚动和交互提示调整，容易恢复且不改变长期产品承诺、业务规则、对象状态、接口、权限、安全、数据或正式范围时，不强制建立REQ或设计评审；在提交、PR或已有任务记录中写清目标、验收和结果即可。

判断时先看能否按既有目标直接处理，再看是否有需要独立追踪的问题或长期产品承诺变化。承诺来自已经确认的设计；页面颜色、位置或文案发生变化，本身不表示承诺改变。

```text
已授权、可恢复的局部调整，或既有设计明确的实现修复
  →实现、验证并报告；不为处理本身建REQ

还不知道是实现缺陷、新需求还是环境问题
  →先调查；需要独立调查、排期或长期追踪时登记ISSUE

需要持续跟踪的新能力或长期规则变化
  →登记REQ，写清期望结果和验收场景
```

如果员工偶尔找不到会话，先检查列表、搜索和已有操作。能够直接修正并验证时，在当前任务记录结果；需要单独继续调查时，ISSUE再保存现象、环境、影响、证据和下一步。

例如，Director要求长思考内容最多320px并内部滚动，原文和折叠行为保持。Agent检查现有组件，调整样式，验证长短内容、键盘滚动和折叠后提交报告即可；不新增REQ、ADR或设计要求编号。若途中需要换会话，留下提交、检查结果和下一步即可。

如果已经确认产品需要提供一种新的方式，让员工主动标记并重新找到重要会话，就可以直接登记REQ，不需要为了流程完整先制造一个ISSUE。REQ是Requirement的缩写，它负责追踪为什么改变产品、希望得到什么结果以及最终进入了哪个正式版本。

ISSUE调查结束后，按既有设计修复，或转入必要的REQ、环境处理；重复、误报和不再处理的问题保留判断依据。编号用于持续跟踪，不代表问题必须转成需求。

## 第三步：把REQ(Requirement)写到Director能够决定是否继续

确实需要REQ时，正文先写清问题、期望结果、非目标和验收场景，帮助Director决定产品怎样改变。已有指令已经说清这些内容时，Agent整理并引用该授权，不为材料的几个小节分别提问；调查和隔离候选也可以继续准备。

以“收藏会话”为例，可以这样表达：

- 问题：员工难以从大量会话中重新找到重要内容；
- 期望结果：员工可以标记自己有权访问的重要会话，之后能够容易地再次找到；
- 非目标：本次不同时建设共享收藏、标签分类和智能推荐；
- 验收场景：员工收藏会话后，刷新页面和重新登录仍能看到收藏状态，并能从列表中优先找到它；取消收藏后恢复普通显示。

这里故意没有决定使用新的数据表还是已有字段，也没有规定接口路径和前端组件。REQ描述产品为什么改变和成功以后能观察到什么，具体实现留给后面的设计。

验收场景也不是一句“功能开发完成”。它要让Director能够实际操作，让Agent能够据此设计测试。例如，重新登录后收藏状态是否保留是一项可观察结果；“接口已经实现”只能证明存在一段代码，不能证明员工的问题得到解决。

需求从出现到进入设计，通常会经过以下状态：

```text
待评估 →候选 →已选中
         ↘不采纳
```

`待评估`表示尚未判断是否值得保留；`候选`表示值得考虑，但现在不一定投入；`已选中`记录Director选择进入设计的决定。状态按实际决定更新，不要求逐个停留或重复确认。多个候选需要比较顺序和依赖时，才使用路线图。

需求被选中时不必承诺目标版本。设计和验收范围明确、准备交付时再登记目标版本；它不能代替真实交付结果。Director的指令已经覆盖产品选择和实施范围时，保存同一份授权，不因更新状态再次确认。

REQ的需求状态和Markdown文档状态表达两件不同的事。`候选`、`已选中`说明需求走到了哪里；`Draft`、`Review`、`Accepted`说明一份文档是否已经可以采用。不要用“设计中”“开发中”作为需求状态，也不要因为REQ正文已经写得完整，就宣称需求已经排期或完成。

## GitHub Issues怎样与本地ISSUE联动

先理解问题，再选择直接处理、必要ISSUE或REQ。GitHub Issues则让不了解蜂巢文档目录的人提交反馈，并在熟悉的讨论和看板入口中查看进展。

GitHub Issues适合接收反馈、继续讨论和查看工作进展。项目外部的参与者可以直接提交看到的现象、复现步骤和期望结果，Director和Agent也可以在其中补充调查线索。

但GitHub Issue不是ACDL中负责维护编号和状态的正式记录。它的标题、正文、标签和打开状态都可能被人工修改，也不能完整表达问题与REQ、ACL、DFL、ERL、版本和环境记录的关系。蜂巢仍然以`docs/03-实施/ISSUE/README.md`中的本地ISSUE台账保存正式编号、状态、严重程度和处理去向。

两者建立关系后各自保留自己的作用：

```text
GitHub Issue
  →接收原始反馈、开展讨论、提供看板入口

ISSUE-六位编号
  →保存正式编号、当前状态和后续去向
```

不是每个本地ISSUE都必须创建GitHub Issue。只在GitHub入口有助于收集反馈、开展讨论或展示进展时建立关联。反过来，GitHub上的普通反馈也不自动成为本地ISSUE；能够在当前讨论中直接判断和处理的内容，无需为了同步而分配编号。

### 从GitHub新反馈建立本地ISSUE

新建的GitHub反馈可以先使用`status:Unregistered`标签。这个标签只表示它还没有通过本地ISSUE登记判断，不是ACDL新增的一种正式问题状态。

Director或Agent先阅读反馈，确认来源、现象和已知事实。如果问题需要单独调查、排期或长期追踪，再用`issue:import`为它取得本地编号；仅换会话继续同一项低风险工作不自动导入。先使用`--dry-run`预览准备写入的文件和编号：

```bash
pnpm issue:import -- --github=42 --repository=xiiiblue/hive-os --category=实现缺陷 --severity=S2 --dry-run
pnpm issue:import -- --github=42 --repository=xiiiblue/hive-os --category=实现缺陷 --severity=S2
```

导入会保留GitHub原始反馈，把它作为问题来源，并在本地ISSUE台账中记录一对一的外部关系。分类和严重程度仍由复核事实决定，不直接照搬提交者的选择。

如果复核后确认它是重复反馈、不属于本项目，或者可以在当前会话内直接处理，就在GitHub中说明判断，不为了让工具产生结果而导入本地。

### 关联两边已经存在的问题

有时问题已经先在DFL、ERL、环境记录或当前开发中取得本地ISSUE编号，后来才出现对应的GitHub Issue。这时不再导入第二个本地问题，而是把两个已有编号关联起来：

```bash
pnpm issue:link -- --id=ISSUE-000036 --github=42 --repository=xiiiblue/hive-os --dry-run
pnpm issue:link -- --id=ISSUE-000036 --github=42 --repository=xiiiblue/hive-os
```

一个本地ISSUE只能关联一个GitHub Issue，一个GitHub Issue也不能同时代表多个本地ISSUE。发现重复入口时，先确定哪个本地ISSUE负责保存正式编号和处理结论，再把其它入口标记为重复并指向它。

关联操作只建立编号之间的关系，不会因为GitHub Issue已经关闭就把本地问题改成`Closed`，也不会用GitHub标签覆盖本地分类和严重程度。

### 从本地ISSUE单向同步到GitHub

建立关联以后，本地ISSUE台账继续由Director和Agent根据调查、实施与验证事实更新。GitHub用于显示结果，不反向决定本地状态。

需要检查两边是否一致时，先运行不带`--apply`的同步命令。它只报告差异，不修改GitHub：

```bash
pnpm issue:sync -- --repository=xiiiblue/hive-os
```

确认差异符合预期后，再明确使用`--apply`更新GitHub：

```bash
pnpm issue:sync -- --repository=xiiiblue/hive-os --apply
```

同步会把本地ISSUE编号写入GitHub标题，更新正文中的受管理摘要和根据本地状态自动生成的标签，并根据本地ISSUE是否已经结束打开或关闭GitHub Issue。`Closed`映射为已经完成；`Not Planned`和`Duplicate`映射为不计划处理；其它本地状态保持GitHub Issue打开。

GitHub提交者的原始反馈正文和人工添加的分类标签会继续保留。同步只修改明确由仓库管理的内容，不把整个GitHub正文重写成本地台账副本。GitHub中的手工关闭、重新打开或改标签也不会反向改写本地事实。

本地ISSUE台账和同步工具的变化进入`main`后，`Sync GitHub Issues`Workflow会读取仓库内容，执行同一套单向同步。这个Workflow只获得修改GitHub Issues所需的权限，不会修改仓库文件，也不影响代码质量检查。

同步失败只表示GitHub展示可能落后。本地ISSUE的编号、状态和处理关系仍以仓库中的台账为准。

## 需求管理结束在哪里

已授权的局部调整在规定检查通过并报告后就可以结束。需要REQ的变化，`已选中`记录产品选择，不表示技术方案或交付版本已经确定。Agent按已有授权继续调查、实现和验证；只有命中根`AGENTS.md`的确认条件时才请求新的决定。

```text
问题或反馈
  →局部目标已经授权：直接处理、验证并报告
  →需要独立调查或排期：登记ISSUE，保存去向
  →需要长期产品取舍：登记REQ，记录选择与验收目标
      →按实际授权继续设计和候选工作
```

下一章继续用“收藏会话”说明需要长期设计的变化怎样找到负责当前答案的文档，以及局部调整怎样直接进入实现。
