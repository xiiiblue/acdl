## 内容简介

Agent已经能够参与需求分析、产品设计、架构讨论、编码、测试、评审和发布。一个想法可以很快变成PoC，继续发展为数万行代码，项目达到10万行的时间也大幅缩短。实现速度的提高并不表示项目更容易长期维护，它只是让规模带来的问题更早出现。本书所说的“有效代码”，是指需要长期维护的项目代码，不包括依赖包、构建产物和可以重新生成的代码。

当长期维护的有效代码接近或超过10万行时，复杂度往往会发生质变。完整上下文已经无法放进一段对话，一个Agent也难以同时理解所有设计和历史决定。一项需求可能穿过多个模块、文档、测试、数据和运行环境；多个Agent并行修改时，还会争用代码、数据库迁移、测试资源和发布环境。

局部测试通过，只能说明当前改动满足了部分条件，不能证明多项改动合在一起以后仍然正常，也不能证明它们已经可以形成正式版本。

规模继续增大以后，另一类问题会逐渐显现：需求、设计、代码和环境可能分别停留在不同阶段，后来接手的Agent不知道哪份内容仍然有效；任务看似完成，却没有保存失败、计划变化和剩余问题；新改动不断进入主线，却很难回答一个版本实际包含什么。此时仅靠更长的Prompt、更完整的聊天记录或人的个人记忆，已经无法维持项目的一致性。

10万行是帮助项目感知复杂度变化的经验尺度，不是机械开关。即使代码更少，只要项目涉及安全、生产数据、多个并行任务或高成本决定，也可能更早遇到同样的问题。

为了解决这些问题，蜂巢建立了ACDL。它把人和Agent从发现问题到形成正式版本的协作过程组织起来，让需求有来源、设计能指导实现、任务可以独立验证、并行工作彼此隔离，最后用真实使用、独立评审和版本验收确认结果。

ACDL不是一条要求所有工作依次通过相同步骤的流水线。新功能需要先确认需求和设计，已有设计明确的实现缺陷可以直接进入修复，文字错误只需要修正和检查，环境故障则先恢复现场。工作改变了什么、风险有多大、需要留下什么证据，决定它应该采用哪条路径。

本书从一个想法如何长成项目骨架讲起，再进入文档建设、需求、设计、实施、并行开发、真实使用、独立评审和版本形成。读者既可以顺序阅读，建立完整认识，也可以根据正在处理的工作直接进入对应章节。

## ACDL是什么

ACDL全称Agent Collaborative Development Lifecycle，中文名称为“Agent协同研发体系”。它是蜂巢根据自身项目规模、参与方式、代码仓库、运行环境和交付要求形成的研发体系，不是从外部直接采用的行业标准。

ACDL中的研发由两类参与者共同完成：

- Director是对方向、取舍、授权和最终结果负责的人。Director不是一个固定岗位，而是会在需求、产品、架构、开发、验证、发布和验收之间切换职责。
- Agent在明确的目标和边界内参与调查、讨论、设计、实施和验证，并把过程和证据整理成后来能够继续使用的项目上下文。

这里的“协同”不只是Director提出要求、Agent生成代码。Director负责判断问题、取舍方案和最终确认，Agent负责调查、推演、实施和复核；双方通过持续对话共同得出结论，再把结论写入文档、代码和测试，并用实际运行结果检查。

一项完整的产品变化通常会经过下面的过程：

```text
发现问题
  →确认需求
    →共同完成产品与架构设计
      →拆成可以独立验证的任务
        →Agent实施并提供证据
          →通过真实使用或独立评审发现遗漏
            →Director确认结果
              →形成由Git标签固定的正式版本
```

这条路线帮助读者建立全局认识，不表示每项工作都必须走到最后。ACDL允许实现、设计和评审根据新证据返回前面的环节，也允许低风险工作在完成必要验证后直接结束。

## 这套体系关注什么

### 让决定先于大规模实现

Agent能够很快产出大量代码，也能很快把一个不清楚的想法变成复杂实现。ACDL先区分问题、需求和方案：Director先决定为什么改变，Director和Agent再共同决定系统应该怎样工作，最后才把已经确认的设计交给Agent实施。

### 把文档作为代码的“源码”

在蜂巢中，需求和已经确认的设计定义代码应该实现什么，Loop启动方案说明这一轮准备怎样修改，实施记录保存实际发生的变化和验证结果。文档拥有编号、状态和相互关系，并由辅助工具检查。Agent不需要依靠一段无限增长的聊天记录猜测项目现状。

### 按任务并行，而不是让多个Agent挤在一起

ACDL把可以独立验证的任务作为并行单位。每个任务使用自己的worktree、起始提交、修改范围和验证结果。多个Agent可以同时推进不同任务，主线再依次接收每个Agent已经完成并验证的整体结果。

### 区分实现完成和结果可信

代码写完、自动化测试通过、环境已经更新、Loop结束和正式版本形成是不同的时刻。ACL(Agentic Coding Loop)负责实施已经确认的改变；DFL(Developer Feedback Loop)由Director通过真实使用发现问题；ERL(Engineering Review Loop)由高阶Agent独立检查固定对象。三种Loop彼此独立，各自回答不同问题。

### 风险越高，检查越完整

ACDL不以文档数量衡量严谨程度。一行安全规则的变化可能需要完整需求和设计，一次大范围机械修改也可能只需要清楚的边界和自动化验证。合适的路径应该留下足以解释决定、复核结果和继续处理问题的记录，不为形式制造多余对象。

## 怎样阅读

### 第一次完整了解ACDL

建议按第1章至第12章顺序阅读。前4章建立背景、项目规模和完整流程的认识，第5章至第11章依次展开需求、设计、实施、评审和版本形成，第12章说明实际工作不走完整流程时怎样选择路径。

附录不属于第一次阅读的必经内容。开始建立REQ、Loop或验证追踪时，再查阅对应附录中的对象关系、字段、状态和命令。

### 正在从零开始建设项目

先阅读第1章至第3章。第2章介绍怎样通过ChatGPT、PoC和MVP让想法逐渐变成项目骨架；第3章说明项目超过早期规模以后，怎样开始建设能够长期维护的文档。

项目方向和骨架尚未稳定时，不需要提前套用完整ACDL。进入多任务协作、长期维护和正式交付以后，再从第4章开始建立完整流程。

### 已经进入蜂巢项目准备工作

先阅读第1章，认识ACDL、Director、Agent和仓库中的规则入口；再阅读第4章，建立一项需求如何走完整个ACDL的全局认识。随后阅读第12章判断当前工作的性质，再进入对应专题章节。

在蜂巢仓库中实际工作时，Agent仍然从根目录[AGENTS.md](../../../AGENTS.md)开始，随后从[文档中心](../../README.md)查找当前有效的需求、设计、实施、版本和环境记录。本书负责解释研发过程，不代替这些当前记录。

本书第1章至第12章及附录A至附录C已经完成审阅，当前状态为`Accepted`，可以作为蜂巢当前ACDL教程使用。后续只改错字、链接、排版和不改变含义的表达时保持`Accepted`；如果教程需要增加或改变研发规则，先修改对应规范并完成评审。

ACDL的正式定义和必须遵守的研发规则以[《版本与开发规范》](../../00-规范/STD-004-版本与开发规范.md)为准。蜂巢当前的需求、设计、实施、版本和环境状态从[文档中心](../../README.md)进入，并以其中列出的唯一事实源为准。本书只解释怎样理解和使用这些规则，不复制不断变化的项目状态。

书中的示例用于解释方法，不代表蜂巢已经承诺对应功能，也不能代替正式REQ、设计、实施记录或版本结论。
