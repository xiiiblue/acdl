>
> 中文名称：Agent协同研发体系

## 1.ACDL解决什么问题

Agent已经能够参与需求分析、设计、编码、测试、评审和发布。实现速度提高以后，项目更容易在很短时间内积累大量代码、文档、测试和环境状态；真正困难的事情逐渐变成：怎样让后来接手的Agent知道哪些决定仍然有效，怎样让多个任务并行而不互相污染，怎样判断一项工作真的完成，以及怎样准确说明一个正式版本到底包含什么。

蜂巢把人和Agent共同参与研发的这套方法称为**Agent Collaborative Development Lifecycle（ACDL）**，中文名称为“Agent协同研发体系”。它是蜂巢根据自己的项目规模、协作方式、代码仓库、运行环境和交付要求形成的研发方法，不是行业标准，也不要求其它项目原样照搬。

ACDL关注的是一项变化怎样从问题走到可信结果：

```text
发现问题或提出想法
  →判断是否需要改变产品
    →确认产品和技术设计
      →拆成可以独立完成和验证的任务
        →Agent实施并保存证据
          →按需要开展真实使用或独立评审
            →确认实际交付范围
              →由Git标签固定正式版本
```

这只是完整产品变化最常见的路线，不是所有工作的固定流水线。已经确认设计的实现缺陷可以直接进入修复；不改变含义的文字错误可以直接修改并检查；环境故障要先保护现场和恢复服务。**实际改变了什么、风险有多大、需要留下什么记录，决定工作应该走多长的流程。**

## 2.ACDL中的两类参与者

ACDL使用两个专用称呼：

- **Director**：对方向、取舍、授权和最终结果负责的人。它不是公司职级，同一个人可以在需求、设计、开发、验证和发布中切换职责。
- **Agent**：在明确目标和边界内参与调查、设计、实施、验证和评审的智能体。

这里的协作不是“Director写需求，Agent照单生成代码”。Agent会调查代码和环境、提出方案并带回新证据；Director根据这些证据继续判断、调整或确认。Agent可以参与决定的形成，但产品取舍、重要技术边界、风险接受和最终结论仍由Director确认。

Agent可能运行在本机工作树中，也可能通过GitHub等托管平台读取仓库、提交远端分支或评审Pull Request。运行位置和产品名称不产生新的ACDL角色，也不自动决定谁更适合一项工作。Director按当前Agent实际拥有的仓库上下文、工具、权限和验证条件分配任务。

例如，可以把ChatGPT作为需求分析、设计整理和独立审查的参与者，把能够访问本机依赖、数据库、容器和真实环境的Agent作为主要实施与验证者。ChatGPT也可以在权限允许时直接准备文档或低风险代码候选，本地Agent也可以参与需求和设计；这只是推荐分工，不是固定职责或流程门禁。

一种按需采用的接力方式是：

```text
Director与ChatGPT收敛问题和候选设计
  →把确认结果写回REQ、设计或ADR
    →本地Agent基于固定起点实施并验证
      →推送候选分支或Draft Pull Request并固定提交
        →ChatGPT或其它独立Agent评审
          →本地Agent修复问题并重新验证
            →Director确认是否接收、合并或发布
```

产品定义仍有明显分歧时，可以把REQ和设计候选放在一个独立的定义Pull Request中，确认并进入主线后再建立实现Pull Request；低风险修改不需要为了套用这条路线机械拆成两个Pull Request。GitHub保存分支、提交、讨论和交接入口，仓库中的REQ、设计、Loop、环境和版本记录仍保存各自负责的正式事实。

## 3.这套体系最重要的几条原则

### 3.1先确认为什么改，再让实现快速展开

一个模糊想法很容易被Agent迅速实现成一套复杂方案。ACDL先区分问题、需求和实现：需要改变产品时先形成REQ和设计；已有设计已经说清正确行为时，则直接修实现，不重复制造需求。

### 3.2把文档作为代码的“源码”

在蜂巢中，文档不只是代码完成后的使用说明。需求和已经确认的设计定义代码应该实现什么，Loop启动方案说明这一轮准备怎样修改，实施、环境和版本记录保存实际发生的变化与状态。从这个意义上说，**文档是代码的“源码”**：Agent不需要依靠一段无限增长的聊天记录猜测项目现状，而是从仓库里的当前文档取得实施依据和历史上下文。

这个说法不表示所有文档都要在编码前写完，也不表示“文档越多越好”。需求和设计主要指导实现；实施、环境和版本记录则主要保存实际发生的事情。每类信息只在负责它的位置完整维护，其它地方做必要摘要并链接过去。

### 3.3按可独立验证的任务并行

多个Agent并行时，基本单位是**任务**，不是Agent数量。一项任务通常对应一轮ACL和一个当前主要Agent；同一任务确实需要不同能力时，推荐在固定提交上串行接棒，避免多个Agent同时改写同一分支。是否另外建立短期分支、worktree或Pull Request，要看并行冲突、远端交接和评审需要。任务必须有明确起点、范围、外部资源和验证结果，目标分支再按依赖顺序接收各项结果。

### 3.4区分“写完”“验证过”“Loop结束”和“正式发布”

代码写完不等于结果可信，自动化测试通过不等于真实使用没有问题，环境已经更新也不等于正式版本形成。

- **ACL（Agentic Coding Loop）**主要完成实现和自动化验证；
- **DFL（Developer Feedback Loop）**由负责人使用固定候选完成真实任务并记录反馈；
- **ERL（Engineering Review Loop）**由没有参与被评内容实施的Agent检查固定提交、差异或版本。

三种Loop彼此独立，不要求每项工作依次全部执行。正式版本则在版本验收时选择实际纳入的工作，并由真实Git标签固定。

### 3.5风险决定检查深度

ACDL不以文档数量、代码行数或Loop数量衡量严谨程度。一行权限代码可能需要完整需求和设计评审；几十个文件的机械重命名可能只需要边界清楚的实施和验证。流程只做到足以解释决定、证明结果并处理剩余风险即可。

## 6.三类设计在ACDL中的位置

蜂巢当前把长期设计分成系统设计、能力设计和横切设计三类：

- **系统设计**回答蜂巢是什么、全局架构怎样组成，以及整个系统共同遵守哪些边界；
- **能力设计**按一项完整能力集中说明用户行为、对象、状态、流程、接口、数据和实现位置；
- **横切设计**说明多个能力共同遵守的安全、数据、接口、审计和部署规则。

三类设计不是每项REQ都必须各新建一份文件。工作从最高受影响范围开始，再检查需要同步的能力细节和横切约束。ADR记录重要选择为什么这样决定，不是第四类设计。

第6章会完整解释这一关系。
