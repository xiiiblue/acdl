## 先找到唯一登记入口

开始实际工作时，先读根`AGENTS.md`和本次需要的规范；需要查询正式对象时，再从`docs/README.md`找到对应登记表。普通维护和局部界面调整直接检查并报告，不为了套用下面的命令补建REQ、ACL、分支或Pull Request。

ACDL中的同一状态只维护一次，不从聊天、提交标题或其它摘要反推。新ACL主记录维护唯一的`轮次状态`，工具将它同步到登记表；登记表提供查找入口，正文保存详细事实。

|要查的对象|查询入口|主要内容|
|---|---|---|
|REQ和路线图|`docs/01-需求/README.md`|REQ编号、需求状态、优先级、目标版本和路线图入口|
|当前设计|`docs/02-设计/README.md`及系统、能力、横切设计目录|Accepted产品与架构结论、ADR、索引和稳定设计要求正文|
|ISSUE|`docs/03-实施/ISSUE/README.md`|问题编号、状态、严重程度、来源和处理去向|
|ACL|`docs/03-实施/ACL/README.md`|ACL编号、整体状态、版本关系、启动方案和记录入口|
|DFL|`docs/03-实施/DFL/README.md`|DFL编号、整体状态、实际环境、执行基线（实际使用的提交、制品和配置）及记录入口|
|ERL|`docs/03-实施/ERL/README.md`|ERL编号、整体状态、评审基线（实际检查的提交或Git标签）和单一主记录入口|
|目标版本与正式版本|`docs/04-版本/产品版本总览.md`|实际纳入范围、验收结论、发布说明和Git标签|
|正式镜像发布物|`docs/04-版本/V0.X-发布物清单.md`|镜像摘要、保存位置、重新取得结果和兼容结论|
|环境|`docs/05-环境/README.md`|当前部署状态、环境变更记录和恢复入口|
|设计要求追踪|`tests/traceability/design-requirements.json`|稳定要求的来源、产生原因、主题和验证关系|

不要在实施根索引复制每轮Loop状态，也不要在追踪账本复制REQ、ISSUE、Loop或版本状态。

## 编号和状态

### 常用编号和文件名

|对象|形式|编号范围|
|---|---|---|
|规范|`STD-三位编号-标题.md`|全局连续，不复用|
|REQ|`REQ-六位编号-需求简称.md`|全局连续，不复用|
|路线图|`RM-三位编号-标题.md`|全局连续，不复用|
|系统设计|`SYS-三位编号-标题.md`|全局连续，不复用|
|能力设计|`CAP-三位编号-标题.md`；专项设计可用`CAP-三位编号-两位子编号`|全局连续，不复用|
|横切设计|`CRS-三位编号-标题.md`|全局连续，不复用|
|ADR|`ADR-四位编号-决定名称.md`|全局连续，不复用|
|设计索引|`IDX-三位编号-标题.md`|全局连续，不复用|
|ISSUE|`ISSUE-六位编号-问题简称.md`|全局连续；详情文件按需建立|
|ACL|`ACL-六位编号-主题实施记录.md`|全局连续；计划版本与身份分开|
|DFL|`DFL-六位编号-主题实施记录.md`|全局连续|
|ERL|`ERL-六位编号-主题评审记录.md`|全局连续|
|发布说明|`V0.X-发布说明.md`|与真实正式版本对应|
|镜像发布物清单|`V0.X-发布物清单.md`|只在实际发布正式镜像时建立|

编号一经使用不回收。文件标题变化时保留原编号；工作停止时保留编号并更新状态，不用删除文件来制造连续编号。

### Markdown文档状态

|状态|含义|常见去向|
|---|---|---|
|`Draft`|内容仍在整理|继续编写，或者进入评审|
|`Proposed`|已经可以评审，等待决定|进入`Accepted`，或者退回修改|
|`Review`|正在评审或等待确认|进入`Accepted`或`Completed`，也可以继续修改|
|`Accepted`|负责人确认，可以在注明范围内采用|规范、产品、设计、ADR、当前手册的常见最终状态|
|`Completed`|计划、记录、版本或材料已经执行结束|Loop计划与记录、正式版本和发布说明的常见最终状态|
|`Withdrawn`|尚未确认的方案或计划已经停止|保留原因和已发生事实|
|`Superseded`|已经被新文档或决定替代|与替代入口建立双向关系|
|`Rejected`|ADR经过评审后明确不采用|只用于ADR|

产品、设计、ADR和规范持续表达当前结论，不使用`Completed`。环境状态随部署持续变化，使用`Review`记录环境当前状态，不用`Accepted`表示环境已经获得批准。

上表是普通Markdown文档的状态。新ACL只使用下文的轮次状态，不另写相同含义的文档状态；历史ACL、DFL和ERL沿用已有结构。

### REQ状态

|需求状态|含义|目标版本|
|---|---|---|
|`待评估`|刚登记，尚未判断是否值得保留|不需要|
|`候选`|值得继续考虑，但当前不一定投入|不需要|
|`已选中`|Director确认可以进入产品与架构设计|不需要|
|`已排期`|设计已经确认，并确定交付顺序和目标版本|必须填写|
|`已完成`|随实际正式版本通过验收|填写实际版本|
|`不采纳`|拒绝、撤回、重复或由其它事项覆盖|不需要，但保存原因和去向|

“设计中”“开发中”和“测试中”不是REQ状态。设计进度从设计文档读取，开发和验证进度从已有Loop或当前交付说明读取。

### ISSUE状态和严重程度

ISSUE可以按实际情况在调查、处理和验证之间变化，不把它强行简化成一条只能向前的流水线。

|状态|什么时候使用|
|---|---|
|`Reported`|来源和现象还需要复核|
|`Triage`|问题已经保留，但还不知道进入REQ、ACL、环境还是其它处理|
|`Ready`|去向已经确定，尚未开始|
|`In Progress`|已经有正在进行的调查或处理|
|`Verification`|修复或处理已发生，尚未取得要求的验证结果|
|`Closed`|结果已经验证并有明确结论|
|`Not Planned`|决定不继续处理，保存原因和替代办法；必要确认按AGENTS判断|
|`Duplicate`|已有其它ISSUE处理同一个问题|

|严重程度|含义|
|---|---|
|`S0`|会造成Secret泄露、越权、跨员工访问、数据损坏、无法恢复或未批准业务写入等必须立即阻止交付的问题|
|`S1`|核心流程不可用或高概率造成严重业务影响|
|`S2`|存在明确缺陷，但仍有可用替代路径|
|`S3`|低影响交互、表达、文档或维护问题|

严重程度表达影响，不等于处理顺序的全部答案。是否阻止某个版本，还要结合版本范围和ERL计划中事先确定的标准判断。

### Loop整体状态

Loop在启动内容已经准备好、但还没有第一次真实执行时可以处于`Ready`；开始执行后进入`In Progress`。现行主要变化是：

```text
Ready →In Progress →Review →Completed
Ready →Withdrawn
In Progress →Withdrawn
Review →In Progress
Review →Withdrawn
历史Accepted →Completed
```

`Review`表示候选、证据和剩余问题已经整理，等待合入、验收或决定；检查失败也可以如实进入，发现缺口后可以回到`In Progress`。`Completed`和`Withdrawn`是最终状态。ACL进入`Completed`还要求已经合入目标分支，并记录实际纳入提交。结果另行记录，不能从`Completed`推断“没有遗留问题”。

新ACL主记录只维护轮次状态，状态工具同步登记表供查询，不再重复文档状态。DFL、ERL及历史计划原有结构继续保留。

## 常用命令

### 运行命令前先检查工具版本、分支和已有修改

项目命令使用`.nvmrc`和`package.json`锁定的Node.js、pnpm。使用nvm时可先运行`nvm use`；其它版本管理器准备相同版本也可以。开始验证前核对：

```bash
node --version
pnpm --version
git status --short
git branch --show-current
git rev-parse HEAD
```

这些命令确认工具版本、已有差异、当前分支和提交。发现不属于本任务的改动时保留，不为了得到干净工作树删除或覆盖。共享工作树先分配不重叠的文件范围，由一位负责人统一验证、提交和推送；固定候选验证或评审期间，所有写入者停止修改。

### 文档和追踪命令

|命令|是否修改文件|用途|
|---|---|---|
|`pnpm docs:check`|否|检查文档结构、编号、状态、路径、链接、ISSUE与ACL关系及设计要求追踪|
|`pnpm trace:check`|否|单独检查稳定设计要求账本、正文、验证入口和生成视图|
|`pnpm trace:render`|是|根据设计正文和追踪账本重建人类可读视图的生成区|
|`pnpm diff:check`|否|检查差异中的空白错误和冲突标记|

修改普通Markdown后运行：

```bash
pnpm docs:check
pnpm diff:check
```

稳定设计要求或追踪关系变化时，先生成视图再检查：

```bash
pnpm trace:render
pnpm docs:check
pnpm diff:check
```

### ISSUE命令

需要跨任务继续跟踪的问题才登记ISSUE。当前任务内修复的普通缺陷，可以在交付说明中报告；决定登记时，先预览编号和文件：

```bash
pnpm issue:new -- --title=问题摘要 --source=反馈来源 --category=实现缺陷 --severity=S2 --dry-run
pnpm issue:new -- --title=问题摘要 --source=反馈来源 --category=实现缺陷 --severity=S2
```

来源记录已经完整保存事实时，可以使用`--registry-only`只登记台账。GitHub新反馈经复核后导入，两边都已有编号时只建立关联：

```bash
pnpm issue:import -- --github=42 --repository=xiiiblue/hive-os --category=实现缺陷 --severity=S2 --dry-run
pnpm issue:link -- --id=ISSUE-000036 --github=42 --repository=xiiiblue/hive-os --dry-run
```

GitHub同步只从本地ISSUE台账流向GitHub。不带`--apply`只报告差异，带`--apply`才修改GitHub：

```bash
pnpm issue:sync -- --repository=xiiiblue/hive-os
pnpm issue:sync -- --repository=xiiiblue/hive-os --apply
```

`issue:new`、`issue:import`和`issue:link`会修改本地登记表和文档，正式执行前优先使用`--dry-run`。同步不会根据GitHub手工状态反向修改本地台账。

### Loop命令

需要持续协调多个工作单元、长期保存重要证据或决定时才建立Loop，不把ACL、DFL、ERL排成每次必走的流水线。当前`loop:new`只创建ACL，身份与版本分开，计划版本尚未确定时填写`未确定`：

```bash
pnpm loop:new -- --version=未确定 --title=主题 --source=工作来源 --goal=本轮目标 --dry-run
pnpm loop:new -- --version=未确定 --title=主题 --source=工作来源 --goal=本轮目标
```

默认创建为`In Progress`；内容已准备好、尚未执行时，增加`--ready`创建为`Ready`。命令生成单一主记录、轮次状态和当前完整起点，来源包含已登记ISSUE时同步处理关系。候选、验证、时间及实际纳入提交由后续工具维护，正文不手工复制整份摘要；`--mainline`和`--with-plan`已经移除。

历史启动字段中的7至40位SHA仍可读取，短SHA必须在对应仓库唯一解析成提交。未知、歧义或只有汇总链接而没有起点时，先核对补完整SHA，工具不会代用当前HEAD。旧记录不批量改写。

DFL和ERL当前不能自动创建文件，需要在各自登记表取得下一编号，并按相应模板建立单一主记录。高风险操作、恢复办法和评审范围直接写入主记录的启动方案。

ACL进入`Review`使用专门入口，DFL和ERL使用通用状态命令。下面用`--dry-run`预览；正式执行时移除该参数，并替换编号和说明：

```bash
pnpm loop:review -- --id=ACL-000039 --dry-run
pnpm loop:review -- --id=ACL-000039 --allow-failed --pending="必需测试失败，等待决定处理方式" --dry-run
pnpm loop:status -- --id=DFL-000002 --status=Review --dry-run
pnpm loop:status -- --id=DFL-000002 --status=Completed --confirm="实际结果已核对，发现项已有去向" --dry-run
pnpm loop:complete -- --id=ACL-000039 --basis=verified --conclusion="完成条件和规定检查通过，无需新确认" --dry-run
pnpm loop:complete -- --id=ACL-000039 --basis=director --conclusion="Director已确认具体决定及接受范围，见记录" --dry-run
```

`loop:review`从启动基线核对整轮变化和最低档位。失败候选需要`--allow-failed`与待决定问题，且实际失败证据仍对应当前完整树、起点及档位；失败后改过内容不能复用。

新ACL结束使用`--basis=verified`或`--basis=director`并填写`--conclusion`。`verified`必须有整轮必需检查的成功证据，没有需要新确认的遗留风险；`director`说明已有决定及接受范围。历史结构和现有DFL、ERL使用`--confirm`记录实际结论，参数不代替确认本身。ACL自动结束默认在`main`执行，要求工作树干净、候选已通过普通合并或快进合并纳入，工具记录真实提交；当前不支持把squash视作候选已纳入。已授权低风险工作检查通过后可以合入`main`并事后报告，必要确认统一按根`AGENTS.md`处理。

### 验证和发布前检查命令

|命令|用途和边界|
|---|---|
|`pnpm verify -- --dry-run`|读取当前差异并预览将选择的验证范围|
|`pnpm verify`|根据当前差异执行不低于要求的验证，并保存能够精确对应被测内容的提交或Git树标识|
|`pnpm verify -- --base=<Git引用>`|把已提交差异纳入验证；ACL代码证据使用本轮启动基线|
|`pnpm verify -- --profile=docs`|执行当前文档检查；不能覆盖本次仍需验证的代码变化|
|`pnpm check`|额外全仓集成检查，执行工具链、分支、CI契约、输入、Lint、依赖、许可证、类型、构建和测试；不单独生成统一证据摘要|
|`pnpm release:preflight`|检查完整发布验证需要的工具链、Docker、Buildx和`linux/amd64`条件|
|`pnpm validate:release`|执行完整平台验证，构建并检查全部产品镜像|
|`pnpm dev:deploy`|51.8开发环境按变更范围发布的统一入口；具体输入、恢复及拒绝条件见环境文档|
|`pnpm process:metrics -- --since=2026-08-01 --until=2026-08-31`|只读统计Loop积压、已完成周期和ACL首次统一验证结果|

普通`code`运行全仓快速静态检查，类型、构建和测试覆盖受影响包及反向依赖；工具变化运行工具测试。锁文件、根配置或无法归属的输入使用全仓范围，`platform`运行全仓及必需数据库检查。Core、Gateway的目录名称本身不触发平台档位。

仅提交代码或补写记录时，工具可组合成功代码证据和当前完整树的成功文档证据。代码证据必须同启动基线、覆盖最低档位，源码、测试、配置、锁文件和工具输入仍相同；当前文档证据可以用不同或无比较起点。只有文档证据或预览计划不能证明代码通过。旧格式证据仍要求完整树精确匹配，并核对起点和档位。

涉及真实PostgreSQL测试时，`HIVE_TEST_DATABASE_URL`必须指向名称以`hive_workspace_test_`开头的PostgreSQL18专用测试库；测试只清理已知测试Schema，迁移测试从全新的当前线路开始。正式发布验证、镜像和环境操作的当前输入条件从《开发与验证》和目标环境记录读取，不把本附录当作环境操作手册。

## 没有辅助命令的状态怎样维护

REQ排期、设计确认、目标版本形成和版本验收没有自动代替责任人判断的状态命令。Agent根据已确认事实更新对应台账和正文，再运行文档检查；新增确认只按根`AGENTS.md`判断。

脚本能够分配编号、检查结构和同步多个文件，但不能判断需求是否值得做、设计是否合理、证据是否充分或版本是否应该通过。为了让命令成功而修改历史结论，比一次检查失败更危险。
