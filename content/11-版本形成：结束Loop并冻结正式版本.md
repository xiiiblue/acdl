# 版本形成：结束Loop并冻结正式版本

> 文档状态：Accepted
>
> 上一篇：DFL与ERL：通过真实使用和独立评审发现遗漏
>
> 下一篇：流程选择：不同工作从哪里开始，在哪里结束

## 停止编码、Loop结束和正式版本是三件事

Agent完成最后一次代码修改时，还要核对结果和证据。测试结果可能尚未整理，环境中可能运行着另一个提交，实际步骤也可能发生了变化。如果只留下“代码已完成”，后续的人仍然不知道哪些结果可以相信。普通低风险工作完成规定检查并报告即可结束，不必先登记Loop或组织正式版本。

已经登记的Loop进入`Completed`，也不表示正式产品版本已经形成。ACL(Agentic Coding Loop)保存实施与验证结果，DFL(Developer Feedback Loop)保存真实任务和反馈，ERL(Engineering Review Loop)保存固定对象的独立评审。结束状态表示本轮已按记录中的依据结束，具体通过、失败、排除和遗留事项仍要读结论。它们可以分别在不同时间结束，不必依次执行。

正式版本回答的是更大的问题：这次准备向使用者交付哪些变化，采用了哪些代码和证据，还有什么限制，以及哪一个Git提交代表这个结果。

```text
停止编码
  →Agent不再增加本轮改动

Loop结束
  →本轮范围、结果、证据和剩余问题已记录，结束依据成立；ACL还已合入目标分支并记录实际提交

正式版本形成
  →若干已结束工作经过版本验收，由Git标签固定
```

这三个时刻可以相隔很久。普通维护的提交或一个已结束ACL可以继续留在`main`；几周以后，Director准备正式版本时再决定是否纳入。环境发布也可以发生在实施中、DFL开始前或正式版本之后，不能代替任务、Loop或版本的结束结论。

## 先让每轮Loop如实结束

结束一轮Loop时，Agent先把启动时的目标和实际结果放在一起看，而不是只检查有没有最新提交。记录需要让Director看懂：

- 本轮从哪个分支和提交开始，最后形成了什么提交或评审对象；
- 实际完成了哪些实施、验证、真实使用或独立评审；
- 哪些测试、发布和复核通过，在哪个环境得到结果；
- 哪些步骤失败、跳过、不适用或与原方案不同；
- 发现了什么问题，哪些已经解决，哪些由ISSUE、REQ、ACL或环境记录继续处理；
- 本轮目标是否达到，以及这个结论不能证明什么。

计划中的步骤没有发生时，写“未执行”并说明影响，不把它从记录中删掉。实施改变了原方案时，保留变化原因和确认结果，不用最后的做法改写启动方案。Loop结束保存的不是一个漂亮故事，而是下一个人能够复核的实际过程。

整理完成后，让Loop进入`Review`。ACL的评审入口从启动基线核对整轮差异和最低验证档位，并检查候选的统一验证证据：

```bash
pnpm loop:review -- --id=ACL-000039 --dry-run
pnpm loop:review -- --id=ACL-000039
```

源码、测试、配置或工具变化使对应代码证据失效；仅补写记录时，可以组合仍适用的代码证据和当前文档证据。工具检查比较起点和输入摘要，不靠人工声明“代码没改”复用结果。

DFL和ERL使用`pnpm loop:status -- --id=轮次编号 --status=Review`，同步登记表和对应记录。

`Review`可以保存待合入的成功候选，也可以保存失败或待决定的候选。例如，ACL的必需检查仍失败，需要先保留候选等待决定时，明确写出未解决事项：

```bash
pnpm loop:review -- --id=ACL-000039 --allow-failed --pending="必需检查仍失败，保留候选等待决定"
```

这个命令不把失败变成通过，也不允许使用`verified`结束。失败先诊断和修复，再定点回归、重跑原验证；修复后通过的历史失败不需要另行接受。必需检查仍失败、跳过或未执行时继续交付，才按根`AGENTS.md`取得Director确认。

结束依据分为两种：客观完成条件和规定验证通过、没有需要新确认的遗留风险时使用`verified`，由执行者事后记录；重要产品取舍、正式决定、主观验收或高风险接受使用`director`，保存Director的实际授权和结论。已有明确决定覆盖本轮时直接记录，不再逐项确认。DFL和ERL满足对应条件后可以结束。ACL还必须先合入目标分支并保存实际纳入提交；分支、Pull Request和独立评审按实际风险选择，不是所有ACL的固定前置步骤。

ACL在目标分支、工作树干净且候选已纳入时，可以使用：

```bash
pnpm loop:complete -- --id=ACL-000039 --basis=verified --conclusion="规定检查通过，无遗留风险" --dry-run
```

需要Director决定时改用`--basis=director`，在`--conclusion`中记录真实授权和接受范围。DFL和ERL使用`loop:status --status=Completed`并提供对应结束依据。历史记录仍使用旧确认字段时，按工具要求填写`--confirm`保存已有决定，不增加一次审批。命令同步登记表和记录，保存真实结束事实；参数不能代替尚未取得的确认。

如果本轮目标已经放弃，使用`Withdrawn`如实停止，不把未完成工作包装成`Completed`。已经发生的调查、修改、失败和证据继续保留，编号也不重新使用。需要继续的部分可以建立新的Loop，并把原记录作为来源。

## 目标版本不是一份提前承诺全部范围的计划

准备组织一次正式交付时，在`docs/04-版本/产品版本总览.md`建立目标版本的`Review`入口。它可以承接准备排期的REQ，也可以承接一组维护提交；不是每次设计确认都要新建目标版本。这个入口只说明当前准备组织哪一次交付，不提前保证所有候选需求和关联Loop最终都会进入。

目标版本、REQ排期和正式版本形成是三个不同动作：

```text
建立目标版本
  →为一次候选交付分配版本号并建立记录

REQ进入已排期
  →确认它准备服务这个目标版本

正式版本形成
  →确认实际纳入的内容，并创建Git标签
```

DFL和ERL记录中的“关联版本”也不是纳入证明。它只保存开始这轮工作时已知的版本背景。一轮DFL可能检查多个版本，一轮ERL也可能在目标版本尚未确定时开始。只有产品版本总览在验收时明确选择，这轮工作才成为该版本的验收证据，或者成为版本形成前必须通过的ERL。

计划版本为`未确定`的ACL同样不会因为合入`main`就自动属于下一个版本。Director准备版本时，可以选择其中与本次交付有关的工作，也可以让其它维护继续留在主线。

## 版本验收先选择实际纳入的内容

准备正式版本时，Director和Agent先从当前目标中筛选实际范围。产品版本总览需要明确列出：

- 实际纳入的变化，以及相应验收场景得到什么结论；已有REQ时链接对应需求；
- 实际纳入的完整提交；已有ACL时链接对应记录；
- 被选作验收证据的DFL和被选作版本形成前必须通过的ERL；
- 版本源码提交、环境实际运行的提交、制品与配置，以及详细证据入口；
- 明确排除的需求、Loop和未完成范围；
- 尚未解决的问题及其影响和处理决定。

被选中的ACL、DFL和ERL需要已经进入`Completed`，历史上已经使用`Accepted`结束的记录可以继续按历史事实处理。同时核对各轮真实结论，不能把已结束但未通过的使用或评审写成通过。还在`In Progress`或`Review`的Loop不能因为“只差确认”就算作已经纳入。

按规范无需REQ或Loop的维护和局部表现调整，可以直接用提交、已有PR和验收结果纳入；没有采用DFL或ERL时说明实际证据，不为形成版本补造对象。

关联同一目标版本但没有被选中的DFL或ERL，不会自动阻止版本。它可能检查了另一个主题，也可能还没有实际执行。Director需要明确排除并说明影响，不能一面忽略未完成范围，一面宣称这些范围已经通过。

以“收藏会话”为例，某个候选版本可以选择收藏需求对应的ACL、一次真实使用DFL，以及固定候选的独立Pull Request评审。实际验证覆盖权限与数据风险，评审发现已经处理时，可以使用这些证据形成版本，不再补造ERL；发布说明只能引用实际存在的结果，不能把普通审查写成一轮未开展的ERL。

## 回到最初问题判断版本是否真的可用

版本验收不是把所有通过的测试结果加在一起。Director和Agent回到已有REQ或任务目标中的问题、期望结果和验收场景，判断当前候选是否真的解决了最初问题。客观结果由证据证明，需要主观判断的效果和重要取舍由Director作出决定。

收藏接口、页面和测试全部通过，却仍然无法让员工从长列表中更快找到收藏会话，这个版本就没有完成最初需求。相反，某项内部重构没有用户可见变化，只要它达到自己的工程目标，也不需要编造一段产品价值证明。

Director还要逐项查看未解决问题。它们不要求全部清零，但必须有清楚决定：

- 在形成版本前修复，并用修复提交、验证证据和必要的ACL更新候选；
- 把受影响功能或场景排除在本版本之外；
- 作为已知限制保留，并说明影响和后续去向；
- 对确实可以接受的剩余风险作出明确决定。

涉及Secret泄露、越权、跨员工访问、数据损坏、无法恢复或未批准业务写入的问题，不能只写进“已知限制”就继续。候选范围需要修复或排除；作为版本形成前必须通过检查的ERL已经规定阻断等级时，也要遵守开始评审前确定的标准。

证据不足时，版本继续保持`Review`。针对缺口补验证、真实使用、独立评审或修复，按记录需要选择Loop，也可以缩小实际范围。达到原定日期、已经投入很多时间和环境运行正常，都不能代替这次判断。

## 确定最终要打标签的提交，并写面向使用者的发布说明

验收范围稳定以后，Agent固定准备打标签的完整提交。这个提交要包含版本结论和发布说明，源码、文档、迁移、配置及生成内容也要与实际验收对象一致。工作树中未提交的修改不能暗中成为版本的一部分。

源码封版按实际差异完成相应统一验证；只有准备交付正式镜像时才要求完整发布验证、镜像构建和内容检查。两种情况都保存能够对应到候选提交或完整Git树的证据。验证过程中候选发生变化，原结果不能继续证明新代码；修复后需要重新选择受影响的验证范围。

详细命令输出继续保存在验证和实施证据中，产品版本总览只汇总实际范围、关键结果、限制、Director结论和入口。不要把每轮测试的详细过程和输出复制进版本文档，也不要让读者为了理解一次发布先阅读几十份实施记录。

每个正式版本另有一份`V0.X-发布说明.md`，面向实际使用者说明：

- 新增了哪些可以观察到的行为；
- 修复了哪些已经存在的问题；
- 有哪些工程、运维、升级或兼容影响；
- 哪些范围没有纳入，当前有哪些已知限制；
- 使用了哪些关键验收和发布验证。

发布说明只写能够从本次范围和证据核实的结果。提交标题写了“优化”，不表示使用者一定能够感知优化；某个DFL没有开展，也不能根据设计预期补写成已经实机通过。没有对应内容的分类可以直接说明没有，不用为了让文档饱满而补造变化。

## Director确认以后用Git标签固定版本

正式版本和标签属于根`AGENTS.md`规定的确认事项。Agent先准备清楚实际范围、验收场景、证据、排除项、剩余问题和发布说明，再取得或核对Director对本次封版的明确授权。已有具体授权覆盖候选和相关操作时直接记录，不为版本结论、标签和状态更新分别重复申请；笼统批准“最近这些工作”不能替代具体范围。

Git标签创建前，产品版本总览和发布说明保持`Review`。Agent先把已经确认的版本结论和发布说明写入准备打标签的提交，再创建指向这个完整提交的`V0.X`标签，并核对标签确实存在、名称正确、指向预期提交。

```text
固定版本候选提交
  →取得或核对Director对实际范围、验收结论和封版的明确授权
    →创建并核对V0.X Git标签
      →记录真实标签和完成状态
```

Git标签让版本获得一个始终指向同一Git提交的固定标识。REQ中的目标版本、ACL编号、GitHub Milestone、Pull Request、发布分支、Docker镜像名称和某个环境的部署状态都不能替代这个标签。

“冻结正式版本”不是禁止仓库继续开发，也不是把所有相关文档变成不可修改。它表示以后提到这个版本时，始终能够回到同一个Git提交、同一份发布说明和同一组验收事实。后来发现问题时按需要调查、修复或形成新版本，不移动旧标签，也不把后续结果追溯写成旧版本当时已经具备。

## 需要可部署镜像时，在标签后固定发布物

源码封版可以在Git标签已经核对后停止，不为了流程完整强制构建镜像。这时发布说明和版本总览直接写“仅源码”，不建空的发布物清单。

要让同一版本成为可部署版本时，Agent在已存在的正式标签上完成下列步骤：

1. 用干净工作树检出标签，再次核对标签的完整提交；
2. 按当前正式构建入口产出完整镜像集，把产品版本和完整提交写入镜像标识；
3. 完成发布验证和镜像检查，取得每个镜像的不可变摘要；
4. 把全部必需镜像保存到构建机之外的企业镜像仓库或SFTP发布物目录；
5. 从登记位置重新拉取或导入，核对摘要、平台和数量；
6. 在`V0.X-发布物清单.md`记录结果及Director对正式镜像集的确认；已有明确发布授权覆盖本组镜像时直接引用，不另行重复确认。

镜像只在构建机存在、只有`:mainline`标签、只完成构建检查，或只已经上传但没有重新取得核对，都不能写成“可部署”。任一步失败时保留失败事实，不移动Git标签；Director可以决定让该版本保持仅源码，或在原标签上修复构建与保存环境后重新产出候选。如果必须改源码、Dockerfile或构建输入，则建立新产品版本，不改写原标签。

源码封版时明确不产镜像，之后也可以从原标签启动一轮独立镜像发布。新清单记录后来实际发生的构建、保存和确认时间，原发布说明保留“封版当时仅源码”的事实，只追加后续发布物入口，不把时间线改写成同时完成。

开发缓存和临时候选能够从固定源码及输入重新构建，不被环境、恢复入口或待复现问题引用，并已保留必要失败证据时，Agent可以自主清理并记录精确对象。正式镜像、归档和被引用制品继续按[STD-009](../../00-规范/STD-009-版本发布规范.md)保护；不因名称带“临时”或“失败”就删除。

## 创建标签后，再更新版本和REQ状态

真实Git标签创建并核对以后，Agent完成最后的状态更新：

- 在产品版本总览中记录实际标签、标签提交、验收结论和已知限制；
- 记录版本是仅源码还是可部署；可部署时链接已确认的发布物清单；
- 把版本及其发布说明从`Review`改为`Completed`；
- 把实际纳入的REQ从`已排期`改为`已完成`；
- 确认本版本采用且没有未关闭阻断问题的相关设计处于`Accepted`；
- 再次核对标签、版本总览、发布说明和实际提交相互一致。

这些状态更新不能提前发生。REQ进入`已完成`表示它已经随正式版本交付，不表示代码已经合并或某轮ACL刚刚结束。发布说明进入`Completed`也以真实存在的Git标签为前提。

正式版本形成后，不代表它已经部署到每个环境。环境记录继续回答某个环境当前运行什么提交、制品和配置，版本记录回答哪个提交经过正式验收。某个环境可以暂时停留在旧版本，也可以在正式版本形成前运行候选用于DFL，两类记录各自回答自己的问题，不能用环境状态代替版本结论。

## 回头检查版本怎样形成

```text
普通维护或各轮Loop完成自己的范围
  →保存实际结果、证据和剩余事项
    →普通工作验证后报告；已有Loop按相应依据结束
      →当前目标已达到，可以停止
      →准备正式交付
        →选择实际提交及已有REQ、Loop和验收证据
          →固定候选，核对验收目标和剩余风险，写发布说明
            →取得或核对Director的具体封版授权
              →创建并核对Git标签，完成版本和实际纳入REQ的状态
                →仅源码：如实结束
                →可部署：从标签产出、保存、重新取得并登记镜像
```

普通工作可以在验证报告后结束，已有Loop也可以单独结束。只有准备正式交付时，才组织版本和标签；向生产或真实外部用户启用仍须另按已有授权和根`AGENTS.md`确认边界处理。下一章将从不同实际任务出发，说明它们应从哪里进入，又在哪里结束。
